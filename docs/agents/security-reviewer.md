## Project Context

**Repo:** `abofs/stonyx-rest-server`
**Framework:** HTTP server module for the Stonyx ecosystem
**Domain:** Express-based REST server handling HTTP routing, CORS, JSON body parsing, authorization hooks, and request middleware for all Stonyx web-facing applications

## Tech Stack

| Layer | Technology |
|-------|-----------|
| HTTP Framework | Express 5 |
| CORS | `cors` npm package (configurable origin and methods) |
| Body Parsing | `express.json()` (built-in) |
| Auth Model | Per-request-class `auth(req, state)` hooks |

## Architecture Patterns

- **CORS configuration surface:** Origins and methods are configurable via `config.restServer.origin` and `config.restServer.methods` — default is `origin: '*'` (wide open) and all standard methods
- **Auth hook execution timing:** Authorization runs AFTER Express route matching, meaning `req.params`, `req.query`, and `req.body` are all populated — auth logic can make decisions based on the full request context. The ordering is a standing hazard as well as a convenience: because the matcher runs first, **any axis on which the matcher is looser than a downstream predicate is a fail-open by construction** — the router dispatches a request the `auth` hook's own comparison would have rejected. That is #47 stated generally, and it is the first thing to check on any change to routing or matching
- **Route-matching strictness (post-#47, post-#50, post-#54):** the three axes named in this bullet are closed. That is a statement about those three axes, not about the class — a fourth axis (percent-encoding) is **live**, see the residuals at the end of this bullet. Two of them are express *settings* — `case sensitive routing` and `strict routing`, applied at **both** construction sites via `applyRouteMatching()` (`src/route-matching.ts`), called from the `RestServer` and `Request` constructors. They do **not** behave the same per site: for `strict routing` the **child** site closes the whole defect alone and the **parent** site closes only `/health/`, because `Router.prototype.use` hardcodes `strict: false` and mount segments are therefore structurally strict-immune (the opposite of `sensitive`, which `use()` forwards; the version-pinned file-and-line citation lives in `docs/project-structure.md` § *Strict routing (#50)*, and nowhere else, so a router upgrade invalidates one line). **The third axis is NOT a setting, and no express setting can express it: `canonicalRoutes` ([#54](https://github.com/abofs/stonyx-rest-server/issues/54), shipped).** `/public` and `/public/` both reach the sub-app with `req.path === '/'`, so a hook comparing `req.originalUrl` rather than `req.path` saw two different strings for a mounted route class — and separately, an **absolute-form** request target (`GET http://host/admin HTTP/1.1`, RFC 9112 §3.2.2) was handed to that hook as the whole URI, on every route registered through `Request.registerCalls()`. Both were measured reaching the guarded handler unauthenticated while `GET /admin` was denied 401. `shouldRejectTarget()` in `src/route-matching.ts` now compares the raw request target against the path express matched, per request, ahead of the `auth` call in `Request.registerCalls()`, and rejects a mismatch with `next('router')`. **Scope limit, by registration site rather than by route:** the check runs inside the handler closure built by `Request.registerCalls()`, so a route registered directly on the parent app gets none of it — `/health` is the only such route in this repo and has no `auth` hook, but `RestServer.instance.api` is a public property, so a consumer registering an authorized route on it directly is outside this control. Flag that on sight.

  **Two residuals remain, and "authorizes on `originalUrl`" is still a live bypass finding on any route class with a param segment.** (i) Only the query string is stripped before comparison, so a hook string-matching `req.originalUrl` against a fixed path will not match `/admin?x=1`; that is the consumer's comparison to own and the module cannot close it without 404ing every `?`-carrying request. (ii) **Percent-encoding is not normalized on either side.** Express decodes neither `req.originalUrl` nor `req.path` — only `req.params` — so for `GET /enc/%73ecret` both `target` and `canonical` are the encoded string, `shouldRejectTarget()` passes it through *by construction*, and a `:param` route then hands the handler the DECODED value while the hook compared the encoded one. Measured on a fixture identical in shape to `test/sample/requests/admin.ts` — hook authorizing on `req.originalUrl` **with the query correctly stripped** — but on a `/:id` route: `GET /enc/secret` → 401, `GET /enc/%73ecret` → **200, guarded handler, unauthenticated**. Identical on `origin/dev`, so this is a residual and not a #54 regression, which is why #54 changed docs here rather than `src/`. Tracked as [#56](https://github.com/abofs/stonyx-rest-server/issues/56) (`priority-critical`). It is **wider** than either axis #54 closed: `%73` defeats a `req.path` hook as well, whereas the mount-root slash and the absolute-form target each defeated only an `originalUrl` hook. Until #56 ships, treat "authorizes on `originalUrl`" **and** "authorizes on `req.path`" as live findings on any class with a param segment — this is precisely the standing hazard stated one bullet above, with the matcher (encoded) looser than the handler's own view (decoded). Param *values* are not normalized either, so `/private/RESTRICTED` reaching a handler is expected, and a mis-cased sub-path is absorbed by a sibling `/:id` route rather than 404ing (a *trailing-slash* miss is not — `/:id` is equally strict, so it is a true 404)
- **Status code response handling:** Integer returns from handlers and auth hooks are sent as HTTP status codes via `sendStatusResponse` — the `statusMap` config can override response bodies for specific codes
- **Sub-app isolation:** Each Request class mounts as an independent Express app, inheriting global middleware (CORS, JSON) but not each other's route-specific middleware

## Live Knowledge

- The default CORS origin is `'*'` — production deployments must override this to restrict allowed origins; the `origin` config accepts both strings and arrays for multiple origins
- Request handlers receive raw Express `req` objects — any header, cookie, or body parsing happens via Express middleware, and handler code must validate inputs since there is no schema validation layer built in
- The `auth` hook returning `undefined` means "authorized" — returning any integer means "rejected with that status code"; a common mistake is returning `0` (falsy but not undefined), which would send a `0` status
- The `redirect` and `pipe` state keys bypass normal JSON response handling — ensure redirect targets are validated to prevent open redirect vulnerabilities, and pipe sources are trusted streams
- Route matching strictness is a security control, not a style choice. `applyRouteMatching()` must keep being called from **both** constructors, and in each case **before any route is registered on that instance** — express materializes a router lazily on first registration, so a setting applied afterwards is silently ineffective, with no throw and no warning. A parent-only fix passes #47's own `DELETE /ANIMALS/22` reproduction while leaving every sub-path open, and does nothing at all for `DELETE /animals/22/`. Flag any PR that moves, drops, or reorders either call, and treat `caseSensitiveRoutes: false` / `strictRoutes: false` / `canonicalRoutes: false` (`REST_CASE_SENSITIVE_ROUTES=false`, `REST_STRICT_ROUTES=false`, `REST_CANONICAL_ROUTES=false`) as re-opening the corresponding URL-authorization bypass. The three flags are separate keys and none implies the others — that separation is deliberate, so a consumer needing slash tolerance is not forced to re-open the case bypass, nor a consumer needing mount-root slash tolerance forced to re-open #50's sub-path bypass; flag any proposal to merge or rename them
- **`canonicalRoutes` has the opposite timing contract to its two siblings, and it must not be "made consistent" with them.** It is read **per request**, inside the handler closure in `Request.registerCalls()`, not once in a constructor. There is no lazy-materialisation hazard for it, so the "must be applied before any route is registered" rule above does **not** apply — and moving `shouldRejectTarget()` into `applyRouteMatching()` would be wrong on both counts: that function's contract is *apply express settings to an app*, and this is neither a setting nor constructor-timed. Three further regressions to flag on sight, each with its own red-able assertion in `test/integration/rest-server-test.ts` AC1: (a) the check **gated inside `if (this.auth)`** — that leaves `GET /public/` at 200 and makes a security control depend on an unrelated consumer choice (AC1.6); (b) the rejection changed from **`next('router')`** to `res.sendStatus(404)` or `Request.sendStatusResponse()` — measured, `sendStatus` answers `text/plain "Not Found"` while a genuine miss answers `text/html`, which is a working **oracle** telling an attacker the route exists but was spelled wrong, and `sendStatusResponse()` additionally re-introduces it for any consumer with a 404 in `statusMap` (AC1.5); (c) the raw target **parsed** before comparison — `new URL(req.originalUrl, base).pathname`, or any other normalising helper — which re-opens the absolute-form vector *by construction*, because it launders the exact string the consumer's hook is exposed to (AC1.3/AC1.4). Likewise flag `req.baseUrl + req.path` used as the left-hand side: it is `/admin/` for **both** spellings of the mount root, so a check built on it cannot see its own defect. Two more, added after the #55 fix round because each was a one-token edit that made **nothing** fail: (d) the check **moved below** the `if (this.auth)` block rather than gated inside it — AC1.6 is on a hookless class and stays green, but a consumer hook with side effects (audit write, rate-limit counter, session refresh) then runs on a request the module is about to reject, and the hook's own status answers the client, which is the same oracle as (b). Measured with it moved: 34 pass / 0 fail while `GET http://HOST/private/failure` answered **505**. Now killed by AC1.11. (e) the `&& req.baseUrl` conjunct dropped from the canonical expression — availability rather than confidentiality, but total: an `index`-mounted class has `req.baseUrl === ''`, so `GET /` compares `'/'` against `''` and the application root 404s. Measured 34 pass / 0 fail both ways before it had a guard. Now killed by AC1.12
- All three flags are guarded `!== false`, not by a truthy check, and all three default to the truthy direction. A truthy check fails **open** for any consumer whose shipped config predates the key. `trustProxy` deliberately differs (`=== 'true'`) — its safe default is *falsy*, so a truthy check already fails closed for it; the rule is "the guard must fail toward the safe value", not "all guards look alike", so preserve the asymmetry rather than flagging it as an inconsistency. The integration tier cannot see a fail-open guard: with the shipped default `true`, a `=== true` guard leaves every integration test green. Only `test/unit/request-test.ts` can distinguish it — #50's AC3 for `strictRoutes`, #47's AC6 for `caseSensitiveRoutes`, #54's AC2 for `canonicalRoutes`. All three cover *two* failure shapes, and the distinction matters: a guard that fails open only when the key is absent as an own property survives a present-and-`undefined` assertion. All three ACs therefore probe the key present-and-`undefined` **and** deleted as an own property, each with a `hasOwnProperty` precondition assertion. Neither `sinon.stub().value()` nor any other sinon call can express the absent case — `stub()` either materializes an own property or throws — so those assertions manipulate `config.restServer` directly and restore the prior own-property state in `afterEach`. Flag any change that weakens any guard's polarity or deletes those unit assertions
- None of the three flags is pinned in `test/config/environment.ts`, deliberately (#43). Pinning them makes an insecure *shipped* default in `config/environment.js` invisible to a green suite — measured for all three keys. Flag any PR that pins them as part of #43 test-isolation work
- `x-powered-by` is disabled on all sub-apps (`api.disable('x-powered-by')`) — this is set in the Request constructor, reducing server fingerprinting
- The `trustProxy` setting directly controls Express's `trust proxy` behavior — when enabled, `X-Forwarded-For`, `X-Forwarded-Proto`, and `X-Forwarded-Host` headers are trusted, which affects IP resolution and protocol detection
- Error handling in handlers uses a basic pattern: thrown errors propagate to Express's default error handler — there is no global error-catching middleware, so unhandled async rejections in handlers may produce unstructured 500 responses
